# 23120252 Stress Test Design — 2026-11-17

Status: **DESIGN ONLY — PENDING HUMAN REVIEW.** No k6 command, HTTP request, account creation, database reset, result file, or evidence was produced for this design.

## 1. Objective and inherited baseline

The test keeps the approved workflow: Login → Search Products → Product Detail → Add to Cart → Checkout → Order History. Task 1A provides a local reference at 10 VU: p95 12.119 ms, 4.9741 requests/s, HTTP failures 0%, and business checks 100%. That run is a baseline only, not a capacity claim.

The Stress test progressively increases concurrency to observe the first repeatable degradation point and the highest tested plateau that remains stable. The configured 40 VU is only the upper bound of this planned run, not the maximum capacity of the SUT.

## 2. Workload model

| Phase | Transition / target | Duration | Cumulative time | Purpose |
|---|---:|---:|---:|---|
| Ramp 1 | 0 → 10 VU | 60 s | 01:00 | Controlled warm-up to Load baseline |
| Plateau 1 | 10 VU | 120 s | 03:00 | Same-run reference plateau |
| Ramp 2 | 10 → 20 VU | 60 s | 04:00 | Increase to 2× baseline concurrency |
| Plateau 2 | 20 VU | 120 s | 06:00 | Observe latency/throughput/errors |
| Ramp 3 | 20 → 30 VU | 60 s | 07:00 | Increase to 3× baseline concurrency |
| Plateau 3 | 30 VU | 120 s | 09:00 | Observe sustained degradation |
| Ramp 4 | 30 → 40 VU | 60 s | 10:00 | Increase to 4× baseline concurrency |
| Plateau 4 | 40 VU | 120 s | 12:00 | Planned upper observation level |
| Recovery ramp | 40 → 10 VU | 60 s | 13:00 | Remove pressure gradually |
| Recovery hold | 10 VU | 60 s | 14:00 | Observe recovery toward reference |
| Ramp-down | 10 → 0 VU | 30 s | 14:30 | Controlled completion |

Think time remains random at 1–3 seconds between requests. Two-minute plateaus support stage comparison while keeping the first exploratory run bounded. The increments are intended to reveal a performance knee instead of jumping directly from 10 to 40 VU.

## 3. Data model and account requirement

The maximum 40 VUs require **40 unique accounts**, mapped by `exec.vu.idInTest - 1` to rows 1–40 of `test-data/stress_accounts.local.csv`. Only 10 accounts currently exist, so **30 additional accounts are required before execution**. Account sharing is rejected because the SUT keeps carts per user in memory and failed logins can lock accounts.

- `stress_accounts.schema.csv` defines `username,password,shipping_address`.
- `stress_accounts.example.csv` contains non-runnable placeholders only.
- `stress_accounts.local.csv` is the required local input and is Git-ignored.
- `products.csv` remains the verified product input.

Proposed later execution sequence: preserve Load evidence; start the approved SUT and let its SQLite seed complete; provision exactly 40 accounts afterward; validate row count, fields, uniqueness, login readiness, empty carts, and order state; then run once with a unique `RUN_ID`. No reset may occur between stages. Passwords/tokens must never enter logs or Git.

At the Load throughput density (217 completed workflows / 2,250 VU-seconds), the planned 19,450 VU-seconds could create roughly 1,875 orders if scaling were linear. This estimate is for data-risk planning, not a predicted result. Checkout does not decrement inventory in the verified SUT, but carts and order history grow during the run. Later plateaus may therefore include cumulative-data cost as well as concurrency cost; this must be disclosed.

## 4. Reuse and implementation

`test-plans/lib/eshop-workflow.js` contains the request flow, JWT propagation, checks, data validation, think time, and failure handling. Stress imports it rather than copying the Load workflow. The completed Load script is intentionally unchanged so its source/evidence remain reproducible. The module can also support a future separately reviewed Spike design.

Every request is tagged with `stress_stage`, `target_vus`, `step`, and `vu`. Plateau metrics expose average/p95 latency, request count/derived RPS, HTTP failed rate, business-check rate, and workflow-success rate for 10/20/30/40 VU. Global metrics include workflow duration, authentication/overload failures, checkout success, and completed workflows.

## 5. Safety guardrails and degradation criteria

Business checks are inherited unchanged: successful login/JWT, product search/detail identity, cart acknowledgement, checkout order ID, and the matching pending order in history.

| Safety guardrail | Limit | Abort behavior |
|---|---:|---|
| Global p95 | < 5,000 ms | Abort after 30 s evaluation |
| HTTP failed rate | < 10% | Abort after 20 s |
| Business checks | ≥ 90% | Abort after 20 s |
| Workflow success | ≥ 90% | Abort after 20 s |
| Authentication failures | 0% | Abort after 1 s; no retry |
| Network/429/5xx overload failures | < 10% | Abort after 20 s |

These are safety aborts, not capacity/acceptance claims. Failed non-authentication workflows retain 1–3 s back-off. Login and checkout are never automatically retried. The operator must stop a later run if backend CPU exceeds 95% for 30 seconds, system memory pressure exceeds 90%, the backend exits, or resource monitoring fails; k6 cannot enforce those external criteria by itself.

The **start of degradation** is the first plateau supported by raw/resource data where at least one occurs:

1. p95 is at least 2× the same-run 10-VU plateau and increases by at least 100 ms, or p95 exceeds 2,000 ms;
2. HTTP failures reach 1%, or business/workflow success falls below 99%;
3. a ≥50% VU increase yields <10% RPS growth while p95 rises ≥50%;
4. backend CPU is ≥85% for 60 seconds, or memory grows across consecutive plateaus and does not recover at the 10-VU recovery hold.

The highest verified stable level is the highest complete plateau satisfying p95 <2,000 ms, HTTP failures <1%, business/workflow success ≥99%, no safety abort, no >10% RPS decline versus the prior plateau, CPU below 85% sustained, and no unrecovered memory trend. It remains only the highest **tested** stable level. A maximum needs a failing higher level plus repeat/bracketing runs.

The primary Stress view is a custom plateau-comparison HTML report, distinct from the Load primary summary/dashboard. It is generated only from actual runtime metrics. CPU/RAM CSV, access log, screenshot, and video remain `PENDING` until execution.

## 7. Senior review and decisions required

| Review point | Assessment / decision |
|---|---|
| Workload exceeds baseline | Yes: 20/30/40 VU are 2×/3×/4× baseline. Approve 40 VU as first-run ceiling. |
| Data sufficiency | Not yet: approve provisioning 30 more unique accounts after clean seed. |
| Generator bottleneck | Possible because k6/backend share a host; monitor both and reject capacity interpretation if the generator saturates. |
| Degradation visibility | Per-plateau metrics support detection; two-minute levels still require repeat runs for confidence. |
| Threshold suitability | Safety aborts are deliberately looser than degradation criteria. |
| Reproducibility | Requires approved 40-account input, reset order, unique run ID, resource monitor, access log, screenshot, and video. |
| Cumulative-data confounder | Approve cart/order-history growth as part of end-to-end stress, or request a separate isolation experiment later. |

Human approval is required for the 40-VU ceiling, 14m30s duration, 30 additional accounts, reset/provisioning order, guardrails, and cumulative-data treatment before execution.
