# Load Test design — 23120252_Load_20261117

**Status:** APPROVED design baseline. The official execution is recorded separately in `../results/load_execution_20261117.md`; this document retains the pre-run design rationale and contains no measured result.

## Workload model

| Phase | Duration | Target VUs | Purpose |
|---|---:|---:|---|
| Ramp-up | 60 s | 0 → 10 | Admit one isolated account approximately every six seconds; avoids an artificial startup spike. |
| Steady load | 180 s | 10 | Observe repeat purchase-confirmation workflow under the proposed normal concurrent usage. |
| Ramp-down | 30 s | 10 → 0 | End the planned workload gradually. |
| Planned stage total | **270 s (4 min 30 s)** | Max 10 | Does not include potential graceful completion after ramp-down. |
| Think time | 1–3 s between workflow requests | — | Random uniform delay represents user reading/decision time and prevents an unrealistically tight request loop. |

The design uses `ramping-vus`, not a constant-arrival-rate executor: the stated objective is ten concurrent end-to-end users with one account per VU. This is an initial load profile, not a measured capacity or endurance threshold. The same script supports `RUN_MODE=verification` for one VU/one iteration only; this changes no default Load parameter and exists solely as a pre-flight functional check.

## Data-flow and VU isolation

| Input/output | Source / owner | Rule |
|---|---|---|
| Account and password | ignored `test-data/credentials.local.csv` | Ten local rows, mapped by `idInTest` 1–10. Never add this file to Git or submission ZIP. |
| Search/product input | committed `test-data/products.csv` | Verified row `1,iPhone,1`; selected object from search supplies cart `id`, `name`, and `price`. |
| JWT | Login response in VU memory only | Passed in `Authorization: Bearer <token>`; never written to output or logs intentionally. |
| Cart | SUT process-memory state, user-scoped | One account per VU prevents cross-user collision. Reset backend/database before every formal campaign because checkout does not clear this SUT cart. |
| Checkout address | ignored account row | Per-user label; no real address or PII. |
| Order ID | Checkout response in VU memory only | Used to assert that `GET /api/orders/my-orders` contains the new pending order. |

## Acceptance criteria

| Criterion | k6 threshold | Interpretation |
|---|---|---|
| Response-time service level | `http_req_duration: p(95)<2000` | Across all HTTP requests, 95% finish under 2,000 ms. |
| HTTP reliability | `http_req_failed: rate<0.01` | Fewer than 1% of k6-defined failed HTTP requests. |
| Business-flow integrity | `business_checks_pass: rate>=0.99` | At least 99% of explicit workflow checks pass. |

These are provisional acceptance thresholds for the initial Load scenario. They are not measured baselines, capacity limits, hardware thresholds, or evidence that the SUT meets them. Validate them against course expectations and stakeholder/SUT requirements before execution.

## Reset and run preconditions

1. Confirm the group-approved workflow is non-duplicated.
2. Confirm SUT remains at the documented commit and local backend is the intended isolated test target.
3. Reset only the local clone database (`HW5/eshop-sut/backend`) using the approved reset procedure; restart backend to clear process-memory carts.
4. Re-provision the ten local accounts after reset, verify all account rows exist, and confirm the product CSV row still resolves.
5. Confirm no previous account lockout is active. Do not intentionally induce failed logins in this Load plan.
6. Start resource monitoring and prepare output destinations only when execution is approved.

## Human-review decisions required

1. Approve k6 rather than install/use JMeter. The proposed Load view is a k6 end-of-test JSON summary; select two distinct k6-equivalent views for Stress/Spike later and confirm that this satisfies the HW05 distinct-report-view requirement.
2. Approve the 10-VU / 60 s / 180 s / 30 s profile and 1–3 s think-time model as representative of initial load.
3. Approve the provisional p95, HTTP-failure, and business-check thresholds; no requirement-derived SLO is presently available.
4. Confirm whether repeated orders per account during the 4.5-minute run are acceptable. This SUT checkout writes an order but does not clear the in-memory cart; the plan deliberately asserts endpoint behavior, not stock/cart business correctness.
5. Confirm the exact reset/provisioning command is allowed for the local clone before any execution.
