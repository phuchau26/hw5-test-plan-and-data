# 23120252 Spike Test Design — 2026-11-18

Status: **DESIGN ONLY — PENDING HUMAN REVIEW.** No k6 command, HTTP request, account/database mutation, raw metric, HTML report, screenshot, or execution result was created by this design.

## 1. Objective and evidence-based context

The approved end-to-end workflow is unchanged: Login → Search Products → Product Detail → Add to Cart → Checkout → Order History. It covers the selected auth-heavy, read-heavy, and transactional endpoint groups through the shared `test-plans/lib/eshop-workflow.js` helper.

Task 1A Load established a 10-VU local reference of p95 12.119 ms and 0% HTTP failures. Task 1B Stress established 40 VU as the highest **tested stable** level in its stepped profile: p95 9.269 ms, HTTP failures 0%, and workflow success 100%. Those results do not establish maximum capacity or predict the effect of an abrupt arrival-rate change. This Spike design tests that different disturbance while keeping the same workflow and existing 40-account limit.

## 2. Workload model

| Phase | VUs | Duration | Cumulative time | Intent |
|---|---:|---:|---:|---|
| Baseline | 10 | 90 s | 01:30 | Establish same-run 10-VU reference before the surge. |
| Spike transition | 10 → 40 | 5 s | 01:35 | Abrupt 4× concurrency arrival; deliberately unlike the Stress 60-s ramps. |
| Spike peak | 40 | 90 s | 03:05 | Short high-concurrency observation period. |
| Recovery drop | 40 → 10 | 5 s | 03:10 | Quickly remove pressure. |
| Recovery hold | 10 | 120 s | 05:10 | Observe return toward the same-run baseline. |
| Ramp-down | 10 → 0 | 30 s | 05:40 | Controlled completion. |

Random think time remains 1–3 seconds between requests. The 5-second transitions make the workload a spike rather than another gradual Stress ramp. The 90-second peak is bounded to reduce unnecessary order growth yet long enough to create phase-separated measurements. The 120-second recovery hold is longer than baseline so two or more 15-second raw-metric windows can be evaluated after the drop.

## 3. Data and account strategy

The profile has a maximum of 40 VUs, so it uses exactly the 40 already-provisioned, independent rows in Git-ignored `test-data/stress_accounts.local.csv`. `exec.vu.idInTest - 1` maps each VU to one row; account sharing is prohibited because carts are user-scoped in memory and repeated login failures can lock an account.

- `test-data/spike_accounts.schema.csv` defines the required columns.
- `test-data/spike_accounts.example.csv` is non-runnable and contains placeholders only.
- `test-data/products.csv` remains the verified product input.
- The design intentionally does not duplicate credentials into a new local file.

If a future proposal needs more than 40 VUs, first obtain human approval to provision one additional unique account per additional maximum VU after a documented backend seed. Do not reuse accounts or provision/reset as part of this design.

Checkout creates orders and the SUT retains user carts/order history; SQLite/order-history growth can therefore confound later phases. With 6,100 planned VU-seconds, the run is shorter than the 19,450 VU-second Stress profile, but order growth is still a real data risk. Before an authorized execution, inspect account lockout state, product availability, cart/order preconditions, and the documented reset/provision sequence. Do not infer inventory behaviour without source/observed confirmation.

## 4. Measurements, checks, and recovery method

The shared helper retains real business checks: login/JWT, search and detail product identity, cart acknowledgement, checkout order ID, and pending order visibility in history. The Spike script attaches `spike_phase` and `target_vus` tags and emits phase-specific request count/RPS, average/p95 HTTP duration, HTTP failed rate, business-check rate, and workflow-success rate for baseline, transition, peak, and recovery.

The custom metric `spike_recovery_first_successful_workflow_ms` records the earliest successful workflow observed during the recovery hold. It is supporting evidence only. The report must calculate the stronger recovery time from raw tagged metrics in consecutive 15-second windows after the 40→10 drop:

1. baseline reference = baseline p95, error rate, and workflow success;
2. a recovery window qualifies when p95 ≤ `max(1.20 × baseline p95, baseline p95 + 20 ms)`, HTTP errors <1%, and workflow success ≥99%;
3. recovery time is the offset from the start of the 40→10 drop to the first of **two consecutive** qualifying 15-second windows.

If no two windows qualify, report recovery as not demonstrated. Do not substitute the first-success metric for this criterion.

## 5. Safety guardrails and interpretation criteria

| Guardrail | Configured limit | Behaviour |
|---|---:|---|
| Global HTTP p95 | <5,000 ms | Abort after 20 s evaluation. |
| HTTP failed rate | <10% | Abort after 15 s evaluation. |
| Business-check pass rate | ≥90% | Abort after 15 s evaluation. |
| Workflow success | ≥90% | Abort after 15 s evaluation. |
| Authentication failures | 0% | Abort after 1 s; never retry login. |
| Network/429/5xx overload failures | <10% | Abort after 15 s evaluation. |

These are safety limits only, not a requirement that the Spike outcome be labelled PASS or a claim about capacity. The operator must also stop an authorized run if backend CPU exceeds 95% for 30 seconds, memory pressure exceeds 90%, the backend exits, or resource monitoring fails.

Spike degradation is reported if the spike peak has p95 >2× baseline and at least +100 ms (or >2,000 ms), HTTP errors ≥1%, business/workflow success <99%, or weak RPS scaling with worsening latency. Recovery is reported separately using the two-window criterion above. A passed 40-VU Stress plateau does not negate a Spike degradation result, because arrival shape is different.

## 6. Outputs and distinct report view

`RUN_ID` is mandatory before execution. The script is designed to produce these paths only when an authorized run occurs:

- `results/raw-k6/23120252_Spike_<RUN_ID>_metrics.json`;
- `results/k6-summary/23120252_Spike_<RUN_ID>_summary.json`;
- `results/k6-console/23120252_Spike_<RUN_ID>_console.txt` (captured by the future run command);
- `results/html-reports/spike-<RUN_ID>/23120252_Spike_<RUN_ID>_phase_timeline.html`.

The HTML view is a phase timeline with baseline, spike, and recovery cards plus the first-success recovery indicator. It is distinct from Load's summary/dashboard view and Stress's plateau-comparison table. The actual recovery-window calculation remains raw-data analysis after an execution; no result has been precomputed.

## 7. Senior review and decisions required

| Review point | Assessment / decision required |
|---|---|
| Suddenness | 10→40 and 40→10 changes occur in 5 s, clearly different from the Stress 60-s increments. Approve this arrival shape. |
| Account sufficiency | Exactly 40 independent accounts are sufficient for max 40 VU. No provisioning is authorized by this design. |
| Meaningful level | 40 VU matches the highest Stress-tested stable level, so the test isolates abruptness rather than silently expanding capacity. Approve this scope. |
| Recovery measurement | Script provides phase tags and first-success indicator; raw-data 15-s windows are required for the recovery-time claim. |
| Thresholds | Abort thresholds are safety guardrails and deliberately looser than degradation/recovery interpretation criteria. |
| Shared host | k6 and backend share a host; monitor both and do not claim backend capacity if generator/system saturation occurs. |
| Reproducibility/evidence | Future run needs unique `RUN_ID`, no-overwrite precheck, PID-specific CPU/RAM CSV, access log, raw JSON, summary, phase-timeline HTML, and a same-frame k6/Task Manager screenshot. |

Human approval is required for the 10/40-VU levels, 5-second transitions, 90-second peak, 120-second recovery hold, safety aborts, reuse of the 40-account file, and recovery-window method before execution.
